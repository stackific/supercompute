Supercompute is a free geo-replicated purpose-built cloud for AI-first workloads that you can self-host on own commodity hardware, inside of your laptop's VM, inside of your NAS. You can achieve high availability even with just _two_ nodes.

All you need is a static IP (because users need to reach your cloud) and a Postgres database with owner role hosted outside of the Supercompute cloud.

This guide gets you from a fresh clone to a working **`dev`** environment: one public static VM.

### Prerequisites

Install the core tools on your Mac, provision one Ubuntu VM with a static public IP, and have a Postgres database with owner role hosted outside of the Supercompute cloud.

- macOS
- [Task](https://taskfile.dev/installation/)
- [uv](https://docs.astral.sh/uv/getting-started/installation/)
- WireGuard tools (`wg`, `wg-quick`)
- 1 x VM/droplet/VPS/root server/EC2 instance with static IP
- External Postgres instance (not installed by this automation)

```sh
brew install go-task/tap/go-task uv wireguard-tools
```

Clone the repository:

```sh
git clone https://github.com/stackific/supercompute.git
cd supercompute
```

:::caution[Resetting the dev environment]

If you already have a working dev environment you set up successfully or otherwise, you must reset it before continuing.

```sh
task dev-reset CONFIRM=reset-dev
```

`dev-reset` may ask for **BECOME password** (macOS sudo) when disconnecting the Mac WireGuard controller. It retries `task down ENV=dev` up to three times (15 seconds apart) so bootstrap SSH can reach nodes when the mesh is flaky, then continues with local cleanup even if remote teardown still fails.

`dev-reset` tears down cluster and WireGuard on dev nodes, disconnects the Mac mesh, removes `.state/dev`, and deletes the dev vault. The VM itself is unchanged (`ops` user, SSH keys, firewall).

To **stop** without wiping vault or local state, use `task down ENV=dev CONFIRM=down-dev` instead — then `task up` brings everything back. See [Task commands](/reference/task/) (`down` vs reset).

After reset, recreate the dev environment:

```sh
task vault-init ENV=dev
task vault-edit ENV=dev   # set vault_database_url
task up ENV=dev
```

:::

### Step 1: Install dependencies

Run `task setup` from the project root to install the locked Ansible environment and fetch the SHA-pinned rathole Linux amd64 binary.

```sh
task setup
```

`task setup` installs the locked Ansible venv and places rathole in `.vendor/rathole/` (copied to Ubuntu nodes later; unused until you add a non-Lima roaming host).

### Step 2: Prepare the dev environment

Set the `sc_*` FQDNs, then fill the static node's public IP and SSH fingerprint.

Edit `inventories/dev/hosts.yml` — one file for project identity and every node. Set the nameserver, API, app, and apps FQDNs (`sc_ns`, `sc_api`, `sc_app`, `sc_apps`). `sc_ns` must have a parent zone (for example `ns.example.com`); that parent is also used for the Mac WireGuard LaunchDaemon label.

Fill placeholders for `static-1` (public IP and SSH host-key fingerprint). Install this public key on the VM with static IP (`ops` user)—same prep as [Adding a public node](/guides/adding-public-node/). Go and do that first.

A completed `inventories/dev/hosts.yml` file looks like this:

<Tabs syncKey="pkg">
<TabItem label="dev">
```yaml
---
all:
  vars:
    project: example
    sc_ns: ns.example.com
    sc_api: sc-api.example.com
    sc_app: sc-app.example.com
    sc_apps: sc-apps.example.com

nodes:
  hosts:
    static-1:
      public_ip: "159.203.27.69" # Public IP of the VM with static IP
      ssh_ed25519_sha256: "SHA256:pRR...e+M" # Server fingerprint
      private_address: 10.217.80.11
```

### Step 3: Configure DNS

Create records matching `sc_ns`, `sc_api`, `sc_app`, and `sc_apps` from Step 2. Leave `example.com` at your registrar. If the DNS is hosted on Cloudflare, do not enable the proxy orange icons.

| Inventory var | Example | Type | Value |
| --- | --- | --- | --- |
| `sc_ns` | `ns.example.com` | A | **static-1** public IPv4 |
| `sc_api` | `sc-api.example.com` | CNAME | `ns.example.com` |
| `sc_app` | `sc-app.example.com` | CNAME | `ns.example.com` |
| `sc_apps` | `sc-apps.example.com` | NS | `ns.example.com` |

Supercompute's Nameserver then serves `*.sc-apps.example.com`.

To use different names, edit those `all.vars` in `hosts.yml`, create matching DNS records, and re-run `task up`.

### Step 4: Initialize the vault

Create the encrypted vault and local password file for dev.

Each environment has its own encrypted vault and local password file. `vault-init` creates both:

```sh
task vault-init ENV=dev
```

This writes `inventories/dev/.vault-pass` (gitignored) and `inventories/dev/group_vars/all/vault.yml` with `vault_meta`, a placeholder `vault_database_url`, and an auto-generated `vault_database_secret`. The first `task up` adds WireGuard keypairs to the vault.

Decrypted `inventories/dev/group_vars/all/vault.yml` looks like this:

```yaml
---
vault_meta:
  project: example
  provider: dev
vault_database_url: postgresql://REPLACE_WITH_USER:PASSWORD@HOST:5432/DATABASE
vault_database_secret: kR7xP2mN9qL4vB8wF3hJ6tY1cZ5aD0eG_sXu
```

#### PostgreSQL database

Point the vault at your external Postgres before the first deploy.

Supercompute needs a Postgres database with owner role hosted outside of the Supercompute cloud.

```sh
task vault-edit ENV=dev
```

`task vault-edit` decrypts `inventories/dev/group_vars/all/vault.yml` in your editor. You should see `vault_meta`, `vault_database_url`, and `vault_database_secret` (WireGuard keys appear after the first `task up`). Replace only `vault_database_url` with your connection URI (same shape as the **dev** tab). Leave everything else unchanged.

Example after you set the database URL:

<TabItem label="dev">

```yaml
---
vault_meta:
  project: example
  provider: dev
vault_database_url: postgresql://app:secret@db.example.com:5432/supercompute
vault_database_secret: kR7xP2mN9qL4vB8wF3hJ6tY1cZ5aD0eG_sXu
```

</TabItem>

```yaml

  project: <project>
  provider: <env>
vault_database_url: postgresql://REPLACE_WITH_USER:PASSWORD@HOST:5432/DATABASE
```

Save and exit the editor:

- **vim/vi** (default on macOS): press <Kbd mac="Esc" windows="Esc" />, type `:wq`, press <Kbd mac="Enter" windows="Enter" />
- **nano**: press <Kbd mac="Control+O" windows="Control+O" />, <Kbd mac="Enter" windows="Enter" />, then <Kbd mac="Control+X" windows="Control+X" />

`task up` rejects the vault-init placeholder in `vault_database_url`.

### Step 5: Bring up the cloud

Deploy the WireGuard mesh and cluster stack to your node.

```sh
task up ENV=dev
```

When it asks for `BECOME password`, enter your macOS password. You can run `task up` multiple times to retry if you have issues, made mistakes, or just want to be sure, because this is a rather long operation yet an idempotent one.

`up` makes `https://sc-app.example.com` available for you to configure the rest of the cluster.

Please note that the speed of operations heavily depends on the network connection between the Mac and the VM and the performance of the VM/server.

### Step 6: SSH to the node

Confirm you can log in to the node over the mesh.

```sh
task ssh ENV=dev NODE=static-1
```

Optional latency check from a node to the Mac mesh peer:

```sh
ping -c 10 -I scwg0 10.217.80.1
```

If you can access the node, you are done with this guide.

Public Task entrypoints are listed with `task --list`. Full reference: [Task commands](/reference/task/).
