Supercompute is a free geo-replicated purpose-built cloud for AI-first workloads that you can self-host on own commodity hardware, inside of your laptop's VM, inside of your NAS. You can achieve high availability even with just _two_ nodes. It was created by Stackific Inc.

All you need is a static IP (because users need to reach you) and an external Postgres.

This guide gets you from a fresh clone to a working local **`dev`** instance: one public VM plus an optional Lima roaming guest on Apple Silicon.

## Quick Start

### Prerequisites

- macOS on Apple Silicon
- [Task](https://taskfile.dev/installation/)
- [uv](https://docs.astral.sh/uv/getting-started/installation/)
- [Lima](https://lima-vm.io/docs/installation/) (for the `dev` roaming guest)
- WireGuard tools (`wg`, `wg-quick`)
- 1 x VM/droplet/VPS/root server/EC2 instance with static IP

```sh
brew install go-task/tap/go-task uv wireguard-tools lima
```

If you already have a working `dev` inventory you setup successfully or otherwise, you must reset it before continuing.

```yaml
task dev-reset CONFIRM=reset-dev
```

If it asks for `BECOME password`, enter your macOS password. It does not change the remote static servers. It removes Lima guests, their dedicated runtime home (`~/.lima/.<project>-dev`), `.state/dev`, and the dev vault. 

### Step 1: Install dependencies

From the project root directory:

```sh
task setup
```

`task setup` installs the locked Ansible venv. On macOS it also ensures `cloudflared` is on PATH when missing (needed only for non-Lima roaming nodes, not Lima guests).

### Step 2: Prepare inventory

Let's start with the project configuration found in `config.yml`. You will need to edit it to match your project with real values even for local development. Use a domain you can control (e.g., `example.com`). Supercompute does not require you to setup a NS server, but it requires a couple of DNS records, which you will see shortly.

Modifying the `config.yml` file in later steps will likely break the automation, so do not edit it unless you know what you are doing.

```yaml
---
project: example
hostname: example.com
nameserver_hostname: ns.example.com
```

Now let's setup the server inventory, which is basically a list of servers you will be using to deploy your applications to.

The default `dev` inventory is for local development on a macOS computer:

- **static-1** — Ubuntu 26.04 public endpoint (`x86_64`)
- **roaming-1** — Lima guest (optional)

Edit `inventories/dev/hosts.yml` and fill placeholders for `static-1` (public IP and SSH host-key fingerprint). Install this public key on the VM with static IP (`ops` user)—same prep as [Adding a public node](/guides/adding-public-node/). Go and do that first.

A completed `inventories/dev/hosts.yml` file looks like this:

### Step 3: Create the Lima guest

```sh
task lima-up
```

This creates a Lima guest on Apple Silicon. It is used to run applications that require aarch64 architecture. It is not optional.

### Step 4: Vault and bring up

```sh
task vault-init PROVIDER=dev
task up PROVIDER=dev
```

`vault-init` creates `inventories/dev/.vault-pass` (gitignored) and the encrypted vault. To create the password file yourself instead (or to copy the value into GitHub Actions secret `ANSIBLE_VAULT_PASSWORD`):

```sh
python3 -c 'import secrets; print(secrets.token_urlsafe(48))' \
  > inventories/dev/.vault-pass
chmod 600 inventories/dev/.vault-pass
```

When it asks for `BECOME password`, enter your macOS password. You can run `task up` multiple times to retry if you have issues, made mistakes, or just want to be sure, because this is a rather long operation yet an idempotent one.

Please note that the speed of operations heavily depends on the network connection between the Mac and the VM and the performance of the VM/server. We tried with dirt cheap VPSes from arbitrary providers and got poor results vs. reputable providers.

For example, a 1 vCPU + 1 GB RAM "regular" (not Intel/AMD) VPS from Digital Ocean took 5 minutes whereas a 8 vCPU + 12 GB RAM VPS from an arbitrary cheap European provider took 20 minutes.

### Step 5: SSH to the nodes

```sh
task ssh PROVIDER=dev NODE=static-1
task ssh PROVIDER=dev NODE=roaming-1
```

If you can access the nodes, you are done. 

Optional: from the VM over the network connection to the Mac and check the latency:

```sh
ping -c 10 -I scwg0 10.217.80.1
```

### Reset local dev

To discard the local Lima guest, controller WireGuard state, `.state/dev`, and
the dev vault, run:

```sh
task dev-reset CONFIRM=reset-dev
```

This is destructive and prompts for the macOS become password as mentioned in the Prerequisites section.
