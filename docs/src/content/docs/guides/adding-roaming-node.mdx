This guide walks through adding a roaming node: Ubuntu at home (or anywhere with a changing public IP). The home router stays closed. Rathole carries bootstrap SSH: the roaming VM dials the first static hub. Two outbound connections replace a public SSH hostname and an inbound WireGuard port:

| Path | What dials out | Where it lands |
| --- | --- | --- |
| Bootstrap SSH | Rathole **client** on the roaming VM | First static hub, **TCP 2333** |
| Mesh traffic | WireGuard on the roaming VM | Public statics, **UDP 51830** |

Your Mac (and GitHub Actions) never SSH to the roaming node's IP. They jump through `127.0.0.1:(61000 + last octet of private_address)` on the hub after the client is up.

The example uses the **prod environment** and host name **`roaming-1`**. Mesh IP `.21` means hub listen port **61021**.

Where you see `ENV=<env>`, replace with your environment name (for example `prod`).

:::note[What this guide does not cover]

- **Lima guests** (`node_lima_guest: true`) — Lima `roaming-1` on a Mac uses [Adding a node roaming on a Mac](/guides/adding-node-roaming-on-a-mac/) instead (Lima-local SSH, no rathole).

:::

### Before you start

You need a working static environment, operator SSH access, an Ubuntu roaming VM, and an external Postgres instance for that environment (configured in the vault before the first deploy).

You need:

1. A working environment (for example **prod**) with at least **one public static node** ([Adding a public node](/guides/adding-public-node/) or [Deploy to production](/start-here/deploy-to-production/)).
2. The same **operator SSH key** already installed on your static nodes (`~/.ssh/<project>-<env>`).
3. `task setup` completed (fetches the SHA-pinned rathole Linux amd64 binary into `.vendor/rathole/`).
4. An Ubuntu **26.04** amd64 machine for the roaming node (VM, NUC, NAS, etc.).
5. An external Postgres instance with owner role hosted outside of the Supercompute cloud.
6. Console or **LAN SSH** to the roaming VM once (to run the generated install script).

Prove SSH to a static node in your environment first:

```sh
task ssh ENV=prod NODE=static-1
```

### Step 1: Prepare the roaming VM (console)

Install Ubuntu, create the ops user, and confirm SSH listens on port 22.

On the roaming machine (local console or temporary LAN SSH):

1. Install **Ubuntu 26.04** amd64.
2. Create user **`ops`**, install your Mac operator public key, passwordless sudo — same commands as [Adding a public node](/guides/adding-public-node/) Step 3.
3. Confirm `sshd` listens on **port 22**:

```sh
sudo ss -tlnp | grep ':22'
```

4. Confirm outbound internet works (TCP to the hub, UDP for WireGuard). Rathole and WireGuard both dial **out**.
5. Record the host-key fingerprint:

```sh
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Copy the full `SHA256:…` value into your password manager.

### Step 2: Open the static hub firewall

The replacement for a home port-forward is inbound access on the **public static hub**, not on your router.

In the cloud provider (or host) firewall for **every** public static that roaming peers will dial, and especially for the **first** static (`static-1`):

| Rule | Why |
| --- | --- |
| Inbound **TCP 2333** on **static-1** from `0.0.0.0/0` (or a wide IPv4 range) | Rathole control. The roaming public IP changes, so a Mac `/32` is not enough. |
| Inbound **UDP 51830** on **every** public static from a wide source | WireGuard. Roaming always initiates to a static `Endpoint`. |
| Inbound **TCP 22** on statics from your Mac `/32` | Hub bootstrap and the jump’s first hop. |

Your home router needs **no** new inbound rules. Stateful outbound TCP/UDP is enough.

On the hub itself, if you also use `ufw`:

```sh
sudo ufw allow 2333/tcp
sudo ufw allow 51830/udp
sudo ufw status
```

Confirm from any network (including the roaming VM) that TCP 2333 on the hub public IP is reachable before you expect the client to stay up. A closed 2333 looks like `rathole-client` restarting forever.

### Step 3: Fill the environment inventory

Add the roaming host and fingerprint to `inventories/<env>/hosts.yml`. Use the **next free** mesh IP in your CIDR (example prod `10.217.79.0/24` → `.21` if `.11` and `.12` are statics). Rathole listens on the hub at `127.0.0.1:(61000 + last octet)` — `.21` → **61021**.

No `public_ip`. No `bootstrap_ssh_host`. No `node_lima_guest`. The hub jump is derived from `static-1`’s `public_ip` plus the mesh last octet.

### Step 4: Install rathole on the hub and render the client script

From the Mac:

```sh
task rathole-client-bootstrap ENV=prod NODE=roaming-1
```

When it asks for `BECOME password`, enter your macOS password. This task is **not** `task up`. Run it from a Mac even when `control_plane: gha` — GitHub Actions cannot copy the install script onto the home VM.

If the vault did not already contain rathole Noise keys and a token for this host, `rathole-client-bootstrap` writes them into `inventories/<env>/group_vars/all/vault.yml`. For a GHA inventory, **commit and push that vault file** before the next Deploy workflow, or the runner will mint different tokens and the client you just installed will not match the hub.

That command:

1. Pins known_hosts for statics (skips roaming until the jump listens).
2. Ensures vault Noise keys and a per-host token.
3. Installs **rathole server** on the first static hub over public SSH.
4. Writes `.state/prod/rathole/roaming-1-install.sh` and `roaming-1-uninstall.sh` (mode `0700`; the install script contains the token — keep `.state/` off git).

On the hub, confirm the server and the per-host listen port:

```sh
sudo systemctl status rathole-server
sudo ss -tlnp | grep 2333
sudo ss -tlnp | grep 127.0.0.1:61021
```

`2333` should be on `0.0.0.0`. `61021` should already be `LISTEN` on `127.0.0.1` (the hub service bind). Jump SSH still fails until the client in Step 5 is connected. If `rathole-server` is inactive, fix this step before copying the script.

### Step 5: Run the install script on the roaming VM

Copy `.state/prod/rathole/roaming-1-install.sh` to the VM and run it as root. The script downloads the same SHA-pinned rathole binary, writes `/etc/rathole/client.toml`, and enables `rathole-client.service`. It retries until it can reach the hub on TCP **2333**.

**If your Mac is on the same LAN as the VM:**

<Tabs syncKey="pkg">
<TabItem label="Example">

```sh
scp .state/prod/rathole/roaming-1-install.sh ops@192.168.1.50:
ssh -t ops@192.168.1.50 'sudo bash ~/roaming-1-install.sh'
```

</TabItem>
<TabItem label="Template">

```sh
scp .state/<env>/rathole/roaming-1-install.sh ops@<roaming-lan-ip>:
ssh -t ops@<roaming-lan-ip> 'sudo bash ~/roaming-1-install.sh'
```

</TabItem>
</Tabs>

**If you only have a local console** (no LAN from the Mac): copy the script onto the VM with a USB stick or the hypervisor clipboard, then:

```sh
sudo bash ./roaming-1-install.sh
```

The script must run as root (`sudo bash`). When it finishes you should see `rathole-client.service` **active**.

To remove the client later, copy `.state/<env>/rathole/roaming-1-uninstall.sh` the same way and run it as root. That stops the service and deletes `/etc/rathole` and `/usr/local/bin/rathole`. It does **not** remove rathole from the hub.

### Step 6: Confirm the reverse tunnel

On the **roaming VM**:

```sh
sudo systemctl status rathole-client
sudo journalctl -u rathole-client -n 50 --no-pager
```

Healthy logs show a connection to `<static-1-public-ip>:2333`. Crash loops usually mean TCP **2333** is still blocked (Step 2) or `rathole-server` is down (Step 4).

On **static-1**:

```sh
sudo ss -tlnp | grep 127.0.0.1:61021
```

You want `127.0.0.1:61021` in `LISTEN`. If jump SSH in Step 7 still gets connection refused, the client is not registered — check `rathole-client` logs and hub TCP **2333**.

### Step 7: Prove jump SSH from the Mac

Ansible does not need an entry in `~/.ssh/config`. Prove the same jump `task up` will use.

Replace the hub public IP with `static-1`’s `public_ip`. The first hop is ordinary SSH to the hub; the second hop is `127.0.0.1:61021` on that hub.

<Tabs syncKey="pkg">
<TabItem label="Example">

```sh
ssh -F /dev/null \
  -o HostKeyAlias=roaming-1 \
  -o IdentitiesOnly=yes \
  -i ~/.ssh/example-prod \
  -o ProxyCommand="ssh -F /dev/null -o IdentitiesOnly=yes -o HostKeyAlias=static-1 -i ~/.ssh/example-prod -W %h:%p ops@203.0.113.11" \
  -p 61021 ops@127.0.0.1 true
```

</TabItem>
<TabItem label="Template">

```sh
ssh -F /dev/null \
  -o HostKeyAlias=roaming-1 \
  -o IdentitiesOnly=yes \
  -i ~/.ssh/<project>-<env> \
  -o ProxyCommand="ssh -F /dev/null -o IdentitiesOnly=yes -o HostKeyAlias=static-1 -i ~/.ssh/<project>-<env> -W %h:%p ops@<static-1-public-ip>" \
  -p 61021 ops@127.0.0.1 true
```

</TabItem>
</Tabs>

It may ask `Are you sure you want to continue connecting (yes/no)?` for `roaming-1` — type `yes` and press <Kbd mac="Enter" windows="Enter" />. Compare the shown fingerprint to Step 1.

This must return with no password prompt (key-based `ops` login). Do not run `task up` until it does.

#### If `true` fails

| Symptom | What to fix |
| --- | --- |
| Inner hop to `static-1` fails | Hub TCP **22**, operator key, `task ssh ENV=prod NODE=static-1` |
| `Connection refused` on `127.0.0.1:61021` | Client not connected; repeat Steps 2, 5, and 6 |
| Hang, then timeout | Hub TCP **2333** still closed from the roaming egress IP |
| Auth failure on the second hop | `ops` authorized_keys on the roaming VM (Step 1) |

#### Checklist before `up`

| Check | OK? |
| --- | --- |
| Hub firewall: TCP **2333** + UDP **51830** (wide source) | |
| `rathole-server` active on `static-1` | |
| Install script ran as root; `rathole-client` active | |
| `ss` shows `127.0.0.1:61021` on the hub | |
| Jump `ssh … ops@127.0.0.1 -p 61021 true` from the Mac | |
| Fingerprint in `hosts.yml` matches the VM | |

### Step 8: Bring up the mesh

If this is a new environment, run `task vault-init ENV=<env>`, then set `vault_database_url` with `task vault-edit ENV=<env>` before the first bring-up.

**Mac control plane** (`control_plane: mac`):

```sh
task up ENV=prod
```

**GitHub Actions** (`control_plane: gha`): do **not** run `task up` on the Mac. Commit `hosts.yml` and `group_vars/all/vault.yml` (if Step 4 added rathole secrets), then Actions → **Deploy** → `up`. The workflow installs the hub server again (idempotent), jumps through the hub, and reconciles the roaming client and WireGuard.

`up` reaches `roaming-1` via the rathole jump when the mesh is down, then over WireGuard after join. Roaming always initiates to the static hub; Mac↔roaming traffic relays through **static-1** (first static by name). `down` leaves rathole running so this jump still works when the mesh is gone.

### Step 9: SSH over the mesh

**Mac control plane:**

```sh
task ssh ENV=prod NODE=roaming-1
```

**GitHub Actions:** there is no Mac WireGuard peer. Re-run Deploy with **verify**, or SSH to a static public IP.

Optional on the roaming node:

```sh
systemctl status supercompute-roaming-dial.timer
systemctl status rathole-client
```

### What to store off-repo

| Secret / artifact | Purpose |
| --- | --- |
| Operator SSH private key | Mac → nodes (same as static nodes) |
| `ssh_ed25519_sha256` for `roaming-1` | Inventory + known_hosts contract |
| Vault password + encrypted `vault.yml` | Mesh keys, rathole Noise keys, tokens |
| `.state/<env>/rathole/<host>-install.sh` | Re-run on a rebuilt VM; contains the token |
| `.state/<env>/rathole/<host>-uninstall.sh` | Stop and remove the rathole client on the VM |

The repository does **not** store rathole tokens in plaintext.
