This guide walks through adding a **roaming** node: Ubuntu at home (or anywhere with a changing public IP), bootstrap SSH through **rathole** on your static hub, and WireGuard that **always dials out** to your public static hub(s).

The example uses the **prod environment** and host name **`roaming-1`**.

Where you see `ENV=<env>`, replace with your environment name (for example `prod`).

:::note[What this guide does not cover]

- **Lima guests** (`node_lima_guest: true`) — Apple Silicon Lima `roaming-1` uses [Get started locally with a roaming node](/start-here/get-started-roaming-node/) instead.
- **DynDNS or port-forwarding UDP 51830** on your home router — roaming nodes never publish a WireGuard dial-in address.

:::

### Before you start

You need a working static environment, operator SSH access, an Ubuntu roaming VM, and an external Postgres instance for that environment (configured in the vault before the first deploy).

You need:

1. A working environment (for example **prod**) with at least **one public static node** ([Adding a public node](/guides/adding-public-node/) or [Deploy to production](/start-here/deploy-to-production/)).
2. The same **operator SSH key** already installed on your static nodes (`~/.ssh/<project>-<env>`).
3. `task setup` completed (fetches the SHA-pinned rathole Linux amd64 binary).
4. An Ubuntu **26.04** amd64 machine for the roaming node (VM, NUC, NAS, etc.).
5. An external Postgres instance with owner role hosted outside of the Supercompute cloud.
6. Hub firewall: inbound **TCP 2333** (rathole control) and **UDP 51830** (WireGuard) wide enough for a changing home IP.

Prove SSH to a static node in your environment first:

```sh
task ssh ENV=prod NODE=static-1
```

### Step 1: Prepare the roaming VM (console)

Install Ubuntu, create the ops user, and confirm SSH listens on port 22.

On the roaming machine (local console or temporary LAN SSH):

1. Install **Ubuntu 26.04** amd64.
2. Create user **`ops`**, install your Mac operator public key, passwordless sudo — same commands as [Adding a public node](/guides/adding-public-node/) Step 3.
3. Confirm `sshd` listens on **port 22**:

```sh
sudo ss -tlnp | grep ':22'
```

4. Confirm outbound internet works (UDP for WireGuard, TCP for rathole). **Do not** forward inbound UDP **51830** on your router.
5. Record the host-key fingerprint:

```sh
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

### Step 2: Fill the environment inventory

Add the roaming host and fingerprint to `inventories/<env>/hosts.yml`. Use the **next free** mesh IP in your CIDR (example prod `10.217.79.0/24` → `.21` if `.11` and `.12` are statics). Rathole listens on the hub at `127.0.0.1:(61000 + last octet)` — `.21` → **61021**.

No `public_ip`. No `bootstrap_ssh_host`. No `node_lima_guest`.

### Step 3: Install rathole on the hub and render the client script

```sh
task rathole-client-bootstrap ENV=prod NODE=roaming-1
```

This ensures vault Noise keys and a per-host token, installs **rathole server** on the first static hub, and writes `.state/prod/rathole/roaming-1-install.sh`.

Copy that script to the roaming VM and run it as root. The client retries until it can reach the hub on TCP **2333**.

### Step 4: Prove jump SSH

Ansible jumps through the hub on `127.0.0.1:(61000 + last octet)`. After the client is up:

```sh
ss -tlnp | grep 127.0.0.1:61021   # on static-1
```

Then `task up` will scan the host key through that jump.

#### Checklist before `up`

| Check | OK? |
| --- | --- |
| `rathole-server` on the static hub | |
| `rathole-client` enabled on the roaming VM | |
| Hub allows inbound TCP **2333** | |
| Fingerprint recorded in `hosts.yml` | |

### Step 5: Static hub firewall

Roaming nodes dial **out** to public statics. Each static VM must allow **inbound UDP 51830** from the internet (or wide enough sources). The rathole hub must also allow **inbound TCP 2333**. TCP **22** on statics stays for Mac/GHA bootstrap to the hub itself.

### Step 6: Vault and bring up

If this is a new environment, run `task vault-init ENV=<env>`, then set `vault_database_url` with `task vault-edit ENV=<env>` before the first `task up`. Existing prod: update `hosts.yml` only, then:

```sh
task up ENV=prod
```

`up` reaches `roaming-1` via the rathole jump when the mesh is down, then over WireGuard after join. Roaming always initiates to the static hub; Mac↔roaming traffic relays through **static-1** (first static by name).

### Step 7: SSH over the mesh

```sh
task ssh ENV=prod NODE=roaming-1
```

Optional on the roaming node:

```sh
systemctl status supercompute-roaming-dial.timer
systemctl status rathole-client
```

### What to store off-repo

| Secret / artifact | Purpose |
| --- | --- |
| Operator SSH private key | Mac → nodes (same as static nodes) |
| `ssh_ed25519_sha256` for `roaming-1` | Inventory + known_hosts contract |
| Vault password + encrypted `vault.yml` | Mesh keys, rathole Noise keys, tokens |

The repository does **not** store rathole tokens in plaintext. `task down` leaves rathole running so mesh-down recovery still works.
