# Docker Swarm template ingress request

I am building a Docker Swarm-based platform that will be offered in two ways:

1. as a hosted SaaS operated by me;
2. as a self-hosted product that customers can deploy in their own infrastructure.

The platform dynamically creates application services. These applications use the same codebase and can all listen internally on port `8080`.

I plan to use Traefik as the ingress/router excluding on the backup node (using run_on_backup=false).

## Current Production Topology

I have three Docker Swarm nodes and only 2 will be exposed thru DNS (1 will be used for backup only).

The nodes are connected to each other over WireGuard.

For public traffic, I intend to point DNS records directly at the public IP addresses of the Swarm nodes for load-balancing purposes.

For example:

```text
*.myapps.com
    |
    +--> node-1 public IP
    +--> node-2 public IP
```

I expect Traefik to run on the edge nodes and route requests such as:

```text
clever-fox-21.templ-prod.supercompute.dev
```

to the appropriate dynamically created Swarm service:

```text
clever-fox-21:8080
```

Multiple applications can use port `8080` internally because Traefik routes to them through the Swarm network rather than through unique published host ports.

## Traefik High Availability

I am considering running Traefik as a Swarm global service so that there is one Traefik instance per eligible node (excluding the backup node, i.e., run_on_backup=false constraint).

For example:

```yaml
deploy:
  mode: global
```

## TLS and Certificate Management

Because I want 2 Traefik instances for HA, I need to understand how TLS certificate management should work.

For the platform-owned domain:

```text
*.templ-prod.supercompute.dev
```

I want a wildcard certificate.

For customer-owned domains, I also want to support hostnames such as:

```text
app.customer.com
```

Customers may use any DNS provider. The solution must not require them to use Cloudflare/AWS.

Concerns I have for are:

### 1. What should act as the Certificate Controller?

I am particularly interested in an implementation using something like:

```text
Go + lego
ACME library
SQLite or similar state storage (any flexibility here?)
S3-compatible object storage (r2, backblaze, wasabi, tigris, etc.)
```

### 2. How should certificates be distributed to Traefik?

If certificates are generated by a separate Certificate Controller:

- Where should the certificate and private key be stored?
- Should they be stored in Docker Secrets?
- Should they be stored on the filesystem?
- Should S3 or another object store be the durable source of truth?
- How should all three Traefik instances receive updated certificates?
- How should renewals propagate without restarting Traefik unnecessarily?

### 3. Is S3 too slow for TLS?

If S3 is used as the durable certificate store, I want to make sure it is **not queried during a live TLS handshake**.

The intended behavior should be closer to:

```text
Certificate Controller
        |
        v
       S3
        |
        v
 certificate sync
        |
        v
 local filesystem
        |
        v
     Traefik
        |
        v
 live TLS traffic
```

I want confirmation that Traefik should resolve certificates from local memory/filesystem during live traffic, with S3 used only for persistence and synchronization.

### 4. Docker Secrets vs mutable certificate state

I also want guidance on what belongs in Docker Secrets versus durable storage.

For example:

Potential Docker Secrets:

```text
DNS API credentials
S3 credentials
ACME credentials
static private keys
```

Potential mutable certificate state:

```text
issued certificates
renewed certificates
customer certificate keys
certificate metadata
```

I want to avoid treating Docker Secrets as mutable certificate storage if that is the wrong model.

## Backup Requirements

My Docker Swarm is already backed up to S3 every six hours.

I want the certificate architecture to fit into this backup strategy.

I need to know:

- which certificate-related state must be backed up separately;
- whether local Traefik certificate files should be considered disposable caches;
- whether the S3 certificate store can be treated as the durable source of truth;
- how Docker Secrets interact with the Swarm/Raft backup;
- what must be restored if an entire edge node is rebuilt.

## SaaS and Self-Hosted Requirements

The architecture needs to work for both:

### Hosted SaaS

Likely:

```text
3+ edge nodes
Traefik on each edge node
wildcard platform domain
customer custom domains
central certificate management
HA
```

### Self-Hosted Customer Deployment

Customers may have:

```text
1 node
```

or:

```text
3+ nodes
```

The self-hosted product should not depend on my own DNS provider, Cloudflare, or my own S3 account.

I want to understand whether the self-hosted version should offer separate modes such as:

```text
single-node / simple ACME mode

multi-node / HA certificate-controller mode

bring-your-own certificate mode
```

## Local Development

My infrastructure is managed through Ansible, and I maintain strong parity between local and production environments.

For local development, I am happy to use:

```text
sslip.io
```

and a local certificate tool such as:

```text
mkcert
```

The local setup should behave as similarly to production as practical:

```text
Traefik
hostname routing
TLS
multiple apps
all apps using internal port 8080
same Swarm labels/config structure
```

The main difference should ideally be only:

```text
local domain
certificate source
environment-specific Ansible variables
```
